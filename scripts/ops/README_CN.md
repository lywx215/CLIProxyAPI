# CLIProxyAPI 逐台更新工具

本工具从 Windows 本机启动，固定一个完整提交，按明确指定的顺序维护 CLIProxyAPI。`init`、`status`、`pause`、`report` 只操作本机；`plan` 做远端只读预检；只有用户明确执行 `update` 或 `resume` 才进入生产维护。没有后台更新、定时任务或默认的“更新全部”。

按 2026-11-12 的更新要求，新计划默认使用文本模型可用性验收。排空的时间兜底上限为 180 秒。独立的配置、健康、模型目录、额度和备份读取并行执行；部署、停流、恢复及回滚仍逐台完成。

离线验收不会连接生产。生产运行的报告分别记录部署、模型验收和渠道恢复；程序已启动或有部分模型通过时，不视为整个维护完成。

## 命令入口

在包含 `cpa-update.ps1` 的仓库根目录执行。需要 Windows 当前用户的 Python 3.11+、Git、Go（版本满足目标提交的 `go.mod`）、Paramiko 和 PyYAML。可用 `-Python` 指定解释器，或设置 `CPA_OPS_PYTHON`。

```powershell
python -m pip install -r scripts/ops/requirements.txt

# 首次配置：输入是只有元数据及 DPAPI 引用的清单；不连接服务器。
.\cpa-update.ps1 init -Inventory C:\private\inventory-input.json

# 只读预检。必须明确目标，并填写 40 位完整提交 SHA。
.\cpa-update.ps1 plan -Targets c05,p3,ultra -Commit <完整40位提交SHA>

# 在同一个队列中为指定目标记录例外。
.\cpa-update.ps1 plan -Targets nc243,nc239 -Commit <完整40位提交SHA> -TargetOptions .\target-options.json

# 下列命令会维护生产。仅在本次获得对应目标的明确更新指令后执行。
.\cpa-update.ps1 update -Plan plan-<编号>

.\cpa-update.ps1 status -Run run-<编号>
.\cpa-update.ps1 pause -Run run-<编号>
.\cpa-update.ps1 resume -Run run-<编号>
.\cpa-update.ps1 report -Run run-<编号>
```

`plan` 输出计划编号；`update` 在开始时输出运行编号。输出采用逐行 JSON，便于接入终端或后续调度器。退出码 `0` 表示完成或已按要求暂停；`2` 表示被阻止、失败或回滚后停止；`130` 表示用户中断。

`pause` 是“当前服务器完成后暂停”，不强行中止流式调用或遗留半套维护。`resume` 先核对远端结果，再继续原状态机。重复 `update` 同一计划会取得原运行记录，不另开一次发布；同一时刻只能有一个执行进程持锁。`status` 和 `report` 可在另一终端使用。

## 本机状态和凭据

默认目录为 `%USERPROFILE%\.codex\private\cliproxy-ops`：

| 路径 | 内容 |
|---|---|
| `inventory.json` | 服务器、固定分支、New API 拓扑和凭据引用；无明文密钥 |
| `credentials/*.dpapi` | 当前 Windows 用户加密的 SSH／New API 管理凭据 |
| `operations.sqlite3` | 事务化计划、阶段、事件、测试结果；敏感快照为 DPAPI 密文 BLOB |
| `releases/<指纹>/release.json` | 固定源码、构建环境、前端／二进制／包摘要及资格检查记录 |
| `reports/<运行编号>/REPORT_CN.html` | 可分享的脱敏 HTML 报告 |
| `reports/<运行编号>/REPORT.json` | 同内容的结构化报告 |

`init` 将已有 DPAPI 引用在内存中校验身份后，重新加密保存到稳定目录，避免长期依赖历史临时脚本。不会修改远端密码、密钥或账号。原引用保留；已存在的清单不覆盖；已存在且内容不一致的凭据副本会阻止初始化。

输入引用支持以下形式。`selector` 定位 JSON 内部记录，`checks` 验证外层身份。明文不得填入清单。

```json
{"path":"C:/private/existing.dpapi","selector":["hosts","192.0.2.1"],"host":"192.0.2.1","checks":{"purpose":"existing-scoped-reference"}}
```

SSH JSON 记录须有 `host/user/port/password`；API JSON 记录须有 `origin/token`。旧版 DPAPI 内直接存 UTF-8 字符串时，加 `"format":"text"` 以及精确的 `host` 或 `origin` 绑定。已有私钥也可通过连接配置的 `identity` 引用，或明确设置 `agent:true`；默认不会遍历本机私钥。

密文只能由原 Windows 用户解密。更换用户或机器时必须重新安全配置，不能将密文当作可跨机的备份。程序没有上传凭据、密钥轮换或复制上游账号的命令。

## 队列和逐台例外

`plan` 并行检查整轮目标，保存 DPAPI 加密备份。进入维护前重新读取当前台的部署、渠道、拓扑、配置和凭证。身份信息匹配时，模型目录可复用至原观测后 10 分钟，已确认的正余额在配额池匹配、观测不超过 120 秒且尚未重置时复用，文件版本一致的凭证备份可复用。无文件版本证据或内容发生变化时重新下载。

当前台排空时仅后台预取紧邻的下一台。全部只读网络操作共享 4 个名额，后台最多占 2 个，当前台排队读取优先。后台预检失败时，先完成当前台恢复，再报告失败目标并停止队列。发布物以完整提交 SHA 固定，在首台停流前完成资格验证和构建。当前入口要求已提交源码。

`-TargetOptions` 接受以本轮目标别名为键的 JSON。例外仅对对应目标生效。省略选项时，执行全部规定模型及恢复候选渠道的测试。

```json
{
  "nc243": {
    "web_model_tests": ["gemini-enterprise-web:gemini-4-argon"],
    "hold_channels": ["vip:22"],
    "fast_model_tests": []
  }
}
```

新计划保存为 schema 2。程序从预检生成路由配置指纹，并在维护前核对。维护基线取当时的原渠道启停状态。旧 schema 1 单目标计划的全局例外继续映射给原目标，多目标且无法归属的旧例外会在停流前报错。

本轮交接记录中的 c03 维护 `run-905f450548a445e2` 最近阻塞于 `k3s_control_plane_certificates_expired`。下一次生产维护前先核对实际租约及远端结果，依恢复流程处理该现场。首轮生产计时在下一次明确授权的单台更新中执行。9 台都走满时间兜底时，180 秒相较 300 秒合计减少 18 分钟，其他收益以实际阶段计时为准。

## 每台服务器的执行步骤

1. **预检**：核对目标身份、固定分支、资源、持久化、OAuth 环境变量、账号模型目录、额度、New API 渠道及实际后端。逐项目／地区匹配公开模型、凭证模型目录和该项目实际选用的配额池；同为 Plus 的其他项目也不能替代目标模型的额度。模型所有可用路径均耗尽、处于额度冷却或明确授权失败时，在停流前阻止执行。余额未知、身份不符或已过重置时间的观测单独标注。预检读到的冷却在采集期间到期时，重新做只读预检确认恢复。
2. **独占与备份** 获取全局维护租约。读到凭证及绑定身份后，并行核对路由、下载备份和读取模型及配额。所有读取合计最多并发 4 项。原始配置、环境和账号文件只进入 DPAPI 加密快照。
3. **准备一次发布物**：从固定 Git 提交导出源码，不打包工作区未提交文件。执行 Go 测试、编译和无上游账号的回环烟测；校验嵌入前端。Linux 包只构建一次，并按完整发布指纹缓存。任何资格检查失败均不会停流。
4. **提前暂存当前服务器**：VPS 上传已校验包，基于旧运行镜像组装薄镜像，禁用拉取和构建联网。保持现有 Compose、环境文件、数据挂载、网络。Zeabur 保存历史成功部署快照。暂存仍在当前服务器的独占窗口内。
5. **停流** 动态分页列出主站和 VIP 中指向该实例域名／IP 的渠道。仅将原先启用的渠道改为停用。主站和 VIP 最多并行执行两项传播任务，写入前持久化操作意图。维护期间复用已核验的 SSH、可复用的 HTTPS 连接和观察器。每个响应完成后保留 2 秒观察时间，批量核验标记归属，歧义样本重新取证。影子后端的缓存同步必须完整发生在该次写入确认之后，并匹配容器启动身份。
6. **排空**：使用下述固定规则，完成后才部署。日志观察失败不算静默。
7. **部署**：重新核对配置、账号身份、进程和分支。仅固定管理页自动更新开关以保证前端摘要稳定。Zeabur 只向绑定分支快进推送；VPS 只执行目标 CLI Compose 服务的重建。
8. **验收**：检查运行程序／镜像、前端摘要、源码部署身份、OAuth、配置与账号设置、模型目录，运行规定的真实模型和逐渠道测试。
9. **恢复**：再次核对外部变动及测试时效，只恢复原先启用且调用成功的渠道，并确认所有实际后端收到恢复。原停用渠道继续停用。
10. **收尾**：检查日志与 New API 进程身份，生成报告，提交完成状态，再释放维护租约。之后才允许进入下一台。

VPS 发布目录是现有根目录下的 `releases/ops-<运行编号>`；只改变 `current.env` 中的 `CPA_IMAGE` 选择。回滚材料、旧镜像和加密快照不会自动清理，磁盘不足会在预检阶段阻止更新。

Zeabur 推送前会重新盘点同仓库的全部服务／环境绑定。查询按环境分别取绑定，用 GraphQL 别名合并多条只读查询，逐条校验响应完整，避免每个服务单独建连拖长维护。总数不符或任一结果缺失均拦截。如果一个分支会触发多个实例，直接阻止；不强推、不自动换分支。自动部署未触发时，重新核实旧部署仍在运行后最多发一次 redeploy。平台回滚只恢复程序构建产物，不恢复环境或持久化数据，参见 [Zeabur 回滚文档](https://zeabur.com/docs/zh-CN/operations/deployment/rollbacks)。

## 排空规则和证据

可靠计数必须覆盖所有提供商、流式、WebSocket 和排队请求。剩余基线请求必须不超过 `floor(基线 × 5%)`；已确认零基线可以立即放行。可靠计数尚未满足条件时，不使用时间兜底绕过；计数中途失效也会停止，不降级伪装成排空成功。

当前已知部署没有可靠的全提供商基线请求清单，生产适配器明确返回“不可用”，因此使用用户已授权的兜底。确认全部停流后，主站和 VIP 的全局请求日志连续 60 秒没有新记录，或等待 180 秒，先满足者放行。最新日志使用完整记录指纹和总数核对；读取失败时使用 180 秒兜底。

报告记录 `request_completion_95_percent`、`newapi_logs_quiet_60_seconds` 或 `fallback_wait_limit_180_seconds` 对应的排空依据。只有可靠计数满足条件时记录 95% 完成。中断续跑会重新连续观察兜底窗口。

主站公网 `:3000` 通过现有 DNAT 直接到达 shadow；域名管理请求通常不会命中这个备用后端。清单保留 `extra_active_backends` 中的 `127.0.0.1:3003`，并启用 `shadow_admin_relay`。程序先核对该端口的 Docker 绑定及公网 DNAT 是否指向同一个 shadow 容器，再经已验证的主机 SSH 标准输入输出建立 TLS。客户端仍校验 `gemini30.pro` 证书及 SNI，服务器只读加载现有证书；无新监听端口或持久配置，不改 Nginx、NAT、DNS，不把管理凭据发往明文公网入口。

该临时通道每次只转发一个限定请求：状态、指定渠道读取，或持锁后原启用渠道的批量状态变更。停流和恢复均检查标记确实到达 shadow、渠道逐条回读一致，并观察状态写入之后的一轮该进程的渠道缓存同步。缓存同步检查属于传播验证，排空等待从传播完成后开始。发现端口／DNAT／进程改变、证书失败、回读不一致或缺少同步证据时拦截。未配置临时通道的额外后端仍须通过常规路径完整覆盖。

首次停流前用严格原始状态核对，避免把维护前外部手工停用的渠道当成自己的操作并在收尾时重新启用。多后端转发或重试导致同一标记落到多个应用时，该样本不作为响应归属证明。

观察器只输出本任务随机标记的 `/api/status` 与渠道状态请求的目标地址，不保存其他业务包、请求头、Cookie 或请求体。SSH 必须匹配已有 `known_hosts`；HTTPS 连接即使固定入口 IP 也保留原域名 SNI／证书校验；不跟随任何授权重定向。

## 调用验收与缓存

模型清单从凭证所属提供商、各启用项目／地区的模型目录和实际公开路由能力生成；不会把名称相似的其他提供商误当成 Enterprise。维护保留全部提供商配置；模型专项验收限定 Gemini Enterprise 和 Gemini Enterprise Web。

- 始终跳过 `gemini-2.5-flash`、`gemini-2.5-flash-lite`；图片、视频、语音、嵌入等专用非文本输出模型单列为排除项。
- 部署验收跳过所有 Claude 模型，包含目录或渠道映射中指向 Claude 的别名。待恢复渠道须使用其他已配置模型通过实际调用。仅配置 Claude 的渠道保持停用，报告标明缺少可验收模型。
- 新计划的 `acceptance_mode` 为 `availability`。全部范围内文本模型各发一次简短流式请求，输出上限 128 tokens，收到非空正文、正常结束且没有错误事件即通过。达到输出上限的正常结束也可通过。
- 公共流式调用还核对已有 `X-CPA-TRACE-ID` 对应的账号／项目身份是否属于目标提供商，避免同名模型实际走了其他渠道。缺少证据或身份不符报 `provider_route_unverified`，不把该调用计为通过；报告不输出原始追踪头。历史版本缺少此证据时需要先另行明确验收办法，工具不静默降低标准。
- Web 在已启用且有 Cookie 时，通过原生 Gemini 流式接口执行同样的简短文本调用。报告标明文本可用性和本次实际覆盖的能力。
- 管理接口将待验收的 Web 凭证标为 `relogin_required` 时，预检会在停流前拦截更新。
- 经明确授权可逐台暂缓仅由失效 Web 凭证提供的指定模型，同时保留同名 Enterprise 测试。依赖该 Web 路径的原启用渠道写入保留停用清单。报告标记 `complete_with_holds`，记录原始状态和待恢复渠道。
- Web 路径已关闭时，可保留明确指定的渠道停用。程序在停流前核实 Web 开关与渠道快照。
- 每条恢复候选渠道在保持停用时，通过 New API 逐渠道管理测试接口调用，校验实际功能成功结果，覆盖该渠道的密钥、映射和参数。范围外提供商的问题也不能成为恢复失败渠道的理由。
- 任一原有必需文本模型消失即阻止恢复；新增范围内模型补测。没有账号的目标不能自动通过模型验收。本次 A/B 直接退役排除。
- 网络抖动／临时 5xx 最多重试一次；401/403、明确额度耗尽、参数错误不盲目重试。不清理冷却、不切换账号停用状态、不改上游开关。
- 单台更新若因指定模型的 HTTP 400 停在模型验收阶段，收到用户明确指示后，可用 `resume -Run <编号> -ExcludeModelTest <提供商:模型>` 记录本次排除。排除项写入报告并在续跑时保留。渠道测试会避开映射到排除模型的别名，并且仍须逐条通过实际调用才能恢复。
- 授权、额度及参数失败直接记录并停止。可用性模式续跑时重新核对目标和配置，再通过实际调用判断失败模型当前是否可用。额度观测未知时记录状态，已知全部路径耗尽或处于冷却时由预检拦截。
- 用户明确要求人工补验时，单台快速计划可指定代表模型。仍核对完整模型目录并逐条实测待恢复渠道，其余模型在报告中标为待人工验证。

当前服务器的模型与渠道测试合计最多并发 2 项。共享项目＋地区池、相同或不能排除重复的 Web Cookie、资源身份不明时串行。可用性模式的成功结果绑定发布物、配置、账号身份及版本和渠道设置，最多复用 10 分钟。续跑补测失败、过期或身份变化的项。渠道调用前确认停流，恢复前再次核对拓扑、渠道状态和测试有效期。

已保存的计划续跑时，使用计划中明确指定的验收方式；缺少 `acceptance_mode` 时默认采用新的可用性验收。报告按各台实际执行的验收方式标注。明确指定的完整模式包含随机校验码和 Web 附件测试，渠道在中断后重新测试。新的 180 秒排空兜底适用于工具后续执行。

报告记录正文／思考字符计数、首正文时间、总耗时、数字 usage、结束状态、允许列出的错误状态码和 `Retry-After` 秒数。不保存原始生成内容、上游错误正文或元数据。报告分开列出失败和尚未调用的模型、渠道。这些小额烟测用于功能验收，不代表长上下文性能或 5000 并发容量压测。

HTML／JSON 记录操作起止时间、缓存命中、重试原因和后台预检失败。操作执行时长按区间并集合并，队列间隔与异常等待单列。服务器完成后的间隔归入队列时间。

## 故障、中断与锁

全局锁固定在 `%USERPROFILE%\.codex\private\newapi\cliproxy-maintenance-active.json`，与旧维护工具共用；另有 OS 进程锁，且检测 `cliproxy-hotconfig-active.json`。改变 `-StateDirectory` 不能绕过全局锁。租约不会因超时自动删除。

| 情况 | 自动行为 |
|---|---|
| 预检、构建或停流前准备失败 | 停止整批，未改渠道；释放本次租约 |
| 停流传播不完整 | 不部署，保留锁和现场，不进入下一台 |
| 已确认部署失败、程序启动失败、程序／前端摘要回归 | 最多回滚一次，重新验收旧程序和渠道；成功恢复原路由后仍停止整批 |
| 授权、额度、上游服务异常或未能归因的功能失败 | 保留相关渠道停用和维护锁，不反复回滚 |
| 回滚响应丢失、失败或结果不明 | 先核对远端结果；不重复盲发平台回滚，不继续下一台 |
| 外部可观察到的配置、账号设置、渠道或拓扑变动 | 停止对齐，不用旧快照覆盖新操作 |

平台或 API 没有配置修订事件时，同一状态被外部重复写入不一定可辨认；工具会比较可获取的完整配置指纹、渠道状态、凭证身份和进程／部署身份，不声称能够识别没有可观察差异的外部操作。维护期间应避免其他人员操作同一目标。

优先用 `status`、`report` 定位失败；处理外部原因后由用户明确执行 `resume`。不要手工删除锁、编辑 SQLite、用旧脚本另开维护或直接 Docker 重建。遇到无法安全恢复的未知结果应继续保留现场，另行核对后再处理。

特别注意：旧版 c03 如果只有 v0 管理接口且没有固定管理页自动更新开关，会在停流前报 `legacy_panel_pin_requires_separate_preparation`。工具不通过已弃用的 v0 全量配置写入去绕开冲突检查；需要一次单独、明确授权的兼容准备。没有为本工具修改应用公开 API 或新增 v0 功能。
